real_talk · an image runtime

Objects that only see what you mount.

real_talk runs images: sets of sandboxed AssemblyScript objects that reach each other only through the paths in their own namespaces. If the image doesn't put something in an object's view, the object can't reach it.

Read the overview → The namespace design
The model

A Plan 9 namespace for every object.

No routing tables and no special syntax for each new kind of connection. Objects send requests to paths, and the image decides what each object can see.

01

Private views

Every instance has its own view: mount points that put another instance's served tree at a path. The image builds it; the instance can rearrange it, but only with names it can already see.

02

Names are the capabilities

A path is resolved in the sender's own view. A name that isn't there is simply not found. Read-only mounts let only safe verbs through, all the way down the chain.

03

The world is a server

The console, TCP and files are servers the runtime implements, configured by the image alone. They are the only way out, and --check prints the most each object can ever reach.

How this page reached you

One request, four hops.

This site is served by the static example image. Here is what happened when you asked for the design page.

  1. 1

    Tcp accepts, http watches

    Environment.Tcp streamed an Accepted to the HTTP server, which watched /net/tcp/<conn> until your whole request had arrived.

  2. 2

    HTTP becomes a namespace request

    GET /docs/ became read /www/docs/ in the server's view, where the image mounted the site. The server knows nothing about files.

  3. 3

    The site forwards

    The site controller added index.html and forwarded the request to /files/docs/index.html in its own view, a read-only mount. It never sees the bytes.

  4. 4

    The packed files answer the caller

    Packed.Files replied with Data from the files built into the image, which went straight back to the HTTP server and out over your connection.

The image

Everything this server can touch.

It touches the host in two ways: one listener, whose address the deployer can change, and the console for the access log. The site itself is packed into the image, and the HTTP server reaches it only through the site controller.

The site also serves a file that exists only in its code. It counts the requests it has forwarded:

–

requests forwarded by the site so far · /hits

require listen : Listen { address: "127.0.0.1:8080" }

instance net   : Environment.Tcp     { send listen }
instance cons  : Environment.Console
instance files : Packed.Files        { include "./public/" }

instance site : StaticSite {
  mount files /files readonly
}

instance http : HttpServer {
  mount net  /net/tcp
  mount site /www
  mount cons /dev/cons
  write /hosts/* Text { text: "/www" }
  write /hosts/files.localhost Text { text: "/www/static" }
}
Try it

Serve these docs yourself.

Requires Rust and Node. The site is the docs, rendered.

make static     # http://127.0.0.1:8080
make site       # re-render the docs into examples/static/public
cargo run -- build examples/static/static.img -o static.rti
cargo run -- static.rti --set listen.address=0.0.0.0:8080
